2 ЗАВДАННЯ 
Метою лабораторної роботи є розробка front-end частини програмної системи, яка повинна підтримувати роботу клієнтів у веб-режимі та забезпечувати адміністрування системи, тобто мати окремий інтерфейс для звичайних користувачів і окремий — для адміністраторів (відповідно до ролей користувачів вашої системи). 


3 ОПИС ВИКОНАНОЇ РОБОТИ 
У процесі розробки веб-застосунку для автоматизації роботи бібліотеки було прийнято ряд архітектурних і технологічних рішень, спрямованих на забезпечення цілісності системи, зручності використання та розширюваності функціоналу. Застосунок реалізовано за клієнт-серверною архітектурою з використанням фреймворку Django, що дозволило організувати чітке розділення між рівнями представлення, бізнес-логіки та доступу до даних. Рівень відображення реалізовано за допомогою Django Templates, які забезпечують серверний рендеринг HTML-сторінок та динамічну підстановку даних у шаблони. Рівень бізнес-логіки представлено у вигляді функцій у файлі views.py, які обробляють HTTP-запити, виконують перевірки, керують логікою роботи системи та взаємодіють з моделями. Рівень доступу до даних реалізовано через Django ORM, що дозволяє працювати з базою даних SQLite у вигляді Python-об'єктів без написання SQL-запитів.
В якості основного технологічного стеку було обрано Django через наявність вбудованої системи автентифікації та авторизації, автоматично згенерованої адміністративної панелі, а також засобів захисту від типових вразливостей, таких як CSRF, XSS та SQL Injection. Для створення користувацького інтерфейсу було використано Bootstrap 5, що забезпечує адаптивний дизайн, готові компоненти інтерфейсу та сучасний вигляд без значних витрат часу на стилізацію.
У системі реалізовано розділення інтерфейсів для різних ролей користувачів. Для звичайних користувачів передбачено доступ до каталогу книг, можливість пошуку, бронювання та перегляду власного профілю. Для бібліотекаря реалізовано окрему панель управління, яка містить функціонал видачі книг, повернення, обробки бронювань та редагування каталогу. Таке рішення дозволяє дотримуватися принципу розмежування доступу та підвищує зручність користування системою. Така структура взаємодії користувачів із системою представлена на діаграмі Use Case (див. рис. Б.1).
Також було прийнято рішення забезпечити інтеграцію веб-застосунку з мобільним застосунком, розробленим раніше, через спільну базу даних. Веб-застосунок на Django та мобільний клієнт взаємодіють з однією базою SQLite, що дозволяє забезпечити узгодженість даних між різними клієнтами та централізовану бізнес-логіку. Це відповідає архітектурі, описаній у попередній лабораторній роботі, де мобільний застосунок взаємодіє з сервером через REST API. Загальна структура взаємодії компонентів системи наведена на діаграмі компонентів (див. рис. Б.2).
Під час розробки також використовувалися інструменти штучного інтелекту. 
Назва інструменту та версія: модель GPT-5.3, план Go. 
Мета використання полягала у прискоренні розробки веб-застосунку, зокрема у розумінні принципів роботи Django, налаштуванні маршрутизації, реалізації системи авторизації, обробці форм та побудові інтерфейсу. ШІ допомагав генерувати приклади коду, пояснював помилки та пропонував варіанти їх виправлення. 
Внесок автора полягав у самостійному інтегруванні отриманих рішень у проєкт, адаптації коду під власну структуру бази даних, налагодженні взаємодії між компонентами системи, тестуванні функціоналу та виправленні логічних і технічних помилок.
Архітектура веб-застосунку базується на патерні MTV (Model-Template-View), який використовується у Django та є адаптацією класичної MVC-архітектури. Взаємодія компонентів відбувається наступним чином. Користувач через браузер надсилає HTTP-запит, наприклад при відкритті сторінки каталогу або виконанні дії, такої як бронювання книги. Django обробляє цей запит через систему маршрутизації, визначену у файлі urls.py, і передає його відповідній функції у views.py. У view виконується основна бізнес-логіка: отримання даних з бази через моделі, перевірка прав доступу, обробка введених користувачем даних та формування відповіді. Послідовність дій користувача та обробка запитів у системі відображені на діаграмі діяльності (див. рис. Б.3).
Моделі, визначені у файлі models.py, описують структуру бази даних і взаємозв’язки між сутностями, такими як користувачі, книги, позики та бронювання. Django ORM виступає посередником між кодом та базою даних, автоматично формуючи SQL-запити при виконанні операцій читання або запису. Наприклад, при виклику Book.objects.all() відбувається запит до таблиці книг, а при збереженні об’єкта виконується операція INSERT або UPDATE. Зміни станів книги в процесі її використання відображено на діаграмі станів (див. рис. Б.4).
Після виконання логіки view передає отримані дані у шаблон через функцію render. Шаблон обробляється системою Django Templates, яка підставляє значення змінних та виконує шаблонні конструкції, після чого формується HTML-сторінка, яка повертається користувачу у браузер.
Окремо реалізовано взаємодію між веб-застосунком і мобільним клієнтом. Як і було показано на UML-діаграмах попередньої роботи, мобільний застосунок надсилає запити до серверної частини через REST API, після чого сервер взаємодіє з базою даних і повертає результат у форматі JSON. Оскільки веб-застосунок використовує ту ж саму базу даних, він автоматично отримує актуальні дані без необхідності додаткової синхронізації. Це дозволяє бібліотекарю в веб-інтерфейсі бачити бронювання, створені з мобільного застосунку, і виконувати з ними подальші дії.
Взаємодія компонентів інтерфейсу реалізована через HTML-форми, які надсилають POST-запити на сервер. Для захисту використовується CSRF-токен, що запобігає підробці запитів. Після обробки запиту застосовується підхід Post/Redirect/Get, що запобігає повторному виконанню дій при оновленні сторінки. Для повідомлення користувача про результати операцій використовується Django Messages Framework. Динамічні елементи інтерфейсу, такі як пошук або підтвердження дій, реалізовані за допомогою JavaScript, але основна логіка обробки даних виконується на сервері, що забезпечує контроль цілісності даних і безпечність системи.

121 # === CRUD: Управління книгами ===
122 @login_required
123 @librarian_required
124 def manage_books(request):
125 # --- СОРТУВАННЯ ---
126     order = request.GET.get('order', 'id')
127     direction = request.GET.get('dir', 'asc')
128 
129     allowed = ['id', 'title', 'author', 'category', 'status']
130 
131     if order not in allowed:
132         order = 'id'
133 
134     if direction == 'desc':
135         order = f'-{order}'
136 
137     books = Book.objects.all().order_by(order)
138     
139     if request.method == 'POST':
140         action = request.POST.get('action')
141         
142         if action == 'add':
143             # Додавання нової книги
144             Book.objects.create(
145                 title=request.POST.get('title'),
146                 author=request.POST.get('author'),
147                 category=request.POST.get('category'),
148                 status='available'
149             )
150             messages.success(request, "Книгу додано!")
151             
152         elif action == 'edit':
153             book_id = request.POST.get('book_id')
154             book = get_object_or_404(Book, id=book_id)
155             book.title = request.POST.get('title')
156             book.author = request.POST.get('author')
157             book.category = request.POST.get('category')
158             book.status = request.POST.get('status')
159             book.save()
160             messages.success(request, "Книгу оновлено!")
161             
162         elif action == 'delete':
163             book_id = request.POST.get('book_id')
164             book = get_object_or_404(Book, id=book_id)
165             if book.status == 'withdrawn':
166                 book.delete()
167                 messages.success(request, "Книгу видалено.")
168             else:
169                 messages.error(request, "Можна видаляти лише списані книги.")
170 
171     return render(request, 'core/librarian/books.html', {'books': books})

173 # === Функція видачі книги (Створення позики) ===
174 @login_required
175 @librarian_required
176 def issue_book(request):
177     if request.method == 'POST':
178         try:
179             user_id = int(request.POST.get('user_id'))
180             book_id = int(request.POST.get('book_id'))
181             days = int(request.POST.get('days', 14))
182             
183             user = User.objects.get(id=user_id)
184             book = Book.objects.get(id=book_id)
185             
186             # 1. Перевірки статусу книги
187             if book.status == 'withdrawn':
188                 messages.error(request, "Книга списана.")
189             elif book.status == 'issued':
190                 messages.error(request, "Книга вже видана.")
191             else:
192                 # 2. Перевірка бронювання
193                 active_res = Reservation.objects.filter(
194                     book=book,
195                     expiry_date__gt=datetime.datetime.now(),
196                     status='active'
197                 ).first()
198                 
199                 if active_res and active_res.user != user:
200                     messages.error(request, f"Книга заброньована користувачем {active_res.user.email}.")
201                 else:
202                     # Якщо броня цього ж юзера - завершуємо її
203                     if active_res and active_res.user == user:
204                         active_res.status = 'completed'
205                         active_res.save()
206                     
207                     # 3. Створення позики
208                     Loan.objects.create(
209                         user=user,
210                         book=book,
211                         due_date=datetime.datetime.now() + datetime.timedelta(days=days)
212                     )
213                     book.status = 'issued'
214                     book.save()
215                     messages.success(request, f"Книга '{book.title}' видана користувачу {user.email}.")
216                     
217         except User.DoesNotExist:
218             messages.error(request, "Користувача не знайдено.")
219         except Book.DoesNotExist:
220             messages.error(request, "Книгу не знайдено.")
221             
222     return redirect('librarian_dashboard')

243                     status='active'
244                 ).order_by('reservation_date').first()
245                 
246                 if next_res:
247                     book.status = 'reserved'
248                 else:
249                     book.status = 'available'
250                 book.save()
251                 
252                 messages.success(request, f"Книга '{book.title}' повернута.")
253         except Loan.DoesNotExist:
